# Phase 10: Autolinking, Monorepos & Native Dependency Resolution

> **Objective:** Deliver zero-config native module discovery, automatic Gradle/CocoaPods linking, transitive dependency resolution, duplicate detection, and native dependency lockfiles (`bloom.lock`).

---

## 🏗️ Architecture: Autolinking & Dependency Pipeline

```text
               bloom add bloom_camera
                         │
                         ▼
        Transitive Dependency Discovery
       (pubspec.yaml + bloom.module.yaml)
                         │
                         ▼
         Duplicate & Conflict Analyzer
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
 Android Autolink  iOS Autolink      bloom.lock
 (settings.gradle) (Podfile)      (Resolved Graph)
```

---

## ⚡ 1. Zero-Config Autolinking (`bloom add <module>`)

When a developer runs `bloom add bloom_camera` or `flutter pub add bloom_camera`:

1. **Discovery:** The Bloom CLI parses `pubspec.lock` and recursively inspects all packages containing a `bloom.module.yaml` manifest.
2. **Native Module Registration:**
   * **Android:** Generates `android/bloom_autolinking.gradle` and automatically includes subprojects in Gradle settings.
   * **iOS:** Generates `ios/BloomAutolinking.podspec.json` and links native pods directly in CocoaPods without manual `Podfile` edits.
3. **Prebuild Execution:** Automatically runs the module's Config Plugin to inject required permissions, Gradle dependencies, and plist entries.

---

## 🌳 2. Transitive Module Discovery

If an application depends on `ecommerce_ui`, and `ecommerce_ui` depends on `bloom_camera`:

```text
my_bloom_app
  └── ecommerce_ui (v2.0.0)
        └── bloom_camera (v1.1.0)  ➔ Autolinked into host app automatically!
```

Bloom's autolinking engine recursively inspects the entire transitive dependency graph, ensuring that nested native modules are linked without requiring explicit declaration in the root `pubspec.yaml`.

## 🚫 3. Duplicate Native Module Detection & Conflict Resolver

Native platforms (Gradle and Xcode) crash with cryptic link errors when multiple versions of the same native binary are included. Bloom detects this **before** invoking the compiler:

```text
✖ Duplicate Native Module Conflict Detected

bloom_camera:
  requested by:
    • package:bloom_shop (root) ➔ requires bloom_camera ^1.2.0 (resolved: 1.2.4)
    • package:qr_scanner_pro    ➔ requires bloom_camera ^1.0.0 (resolved: 1.0.8)

Suggested Actions:
  Run `bloom why bloom_camera` to inspect dependency chains.
  Run `bloom resolve bloom_camera` to automatically align version constraints.
```

### Dependency Explanation: `bloom why <module>`
```bash
bloom why bloom_camera
```
**Output:**
```text
bloom_camera (v1.2.4)
├── dev.bloom.shop (root)
└── ecommerce_suite (v2.1.0) ➔ requires bloom_camera ^1.2.0

Native Dependencies:
  • Android: androidx.camera:camera-camera2:1.3.1 (CameraX)
  • iOS: AVFoundation.framework
```

## 🔒 5. Native Dependency Lockfile (`bloom.lock`)

To guarantee reproducible builds in CI/CD pipelines, Bloom generates `bloom.lock`:

```yaml
# AUTO-GENERATED BY BLOOM CLI. DO NOT EDIT.
lockfile_version: 1
bloom_version: 1.0.0
flutter_version: 3.27.0
dart_version: 3.6.0

native_modules:
  bloom_camera:
    version: 1.2.4
    source: path
    path: packages/bloom_camera
    fingerprint: "a8f9c1b3d2e5..."
    android:
      min_sdk: 24
      target_sdk: 34
      dependencies:
        - "androidx.camera:camera-camera2:1.3.1"
    ios:
      min_version: "15.0"
      frameworks:
        - AVFoundation
```

## 🏢 6. Monorepo & Workspace Support

Bloom natively understands multi-package Dart and Flutter workspaces:

```text
my_workspace/
├── apps/
│   ├── customer_app/
│   └── courier_app/
├── packages/
│   ├── shared_ui/
│   └── api_client/
└── modules/
    └── custom_hardware_scanner/
```

### Workspace Commands
* `bloom workspace status` — Discovers all apps, packages, and native modules in the monorepo.
* `bloom workspace deps` — Builds a unified dependency graph across all internal and external packages.
* `bloom workspace prebuild` — Prebuilds all applications in parallel.
* `bloom workspace test` — Runs tests across all workspace packages with topological execution ordering.

---

## 🧪 Verification & Acceptance Criteria

1. Installing a package containing `bloom.module.yaml` links Android and iOS native targets without manual `build.gradle` or `Podfile` edits.
2. Transitive native dependencies are discovered and linked into the host application.
3. Version collisions between conflicting native modules fail fast with actionable `bloom resolve` suggestions.
4. `bloom.lock` captures deterministic native module fingerprints, SDK constraints, and build versions.
